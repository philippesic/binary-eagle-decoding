# 03: Drafting, batching, and scheduling policies

Local-only analysis, 2026-09-25. No web, GPU, SSH, implementation, or repository edits. Inspected parent `7ae1cc2e4e5ce5f1e3070377722d679d15bc486e` and llama.cpp `34e21b7d85c17e25d5a91ce2ab1074d4c18bfe39`. This report proposes later experiments; it does not amend the active W1Ax protocol or claim new measurements.

## Main conclusion

First measure complete round cost, then tune short chain length and make per-sequence caps avoid actual draft work. The best scheduling opportunity specific to this implementation is to defer draft feature processing/cache reconstruction until the accepted prefix is known. Native EAGLE already batches independent requests at each autoregressive step, so multi-request batching is a useful separate serving experiment rather than a missing single-request feature. Tree expansion and block proposal deserve later, separately gated studies. Neither can be justified merely because a larger matrix runs faster.

For single-request latency, the measured all-nine W1A1 problem is overwhelmingly poor prefix survival. A longer chain or more efficient execution of its existing predictions cannot recover a wrong first proposal. Wider trees could recover alternatives but spend target rows and cache memory to do so. Quality recovery and cheap early abandonment have a stronger evidence basis than blanket width/depth growth.

## What the actual native path does

1. **Chains, with independent-sequence batching.** `common/speculative.cpp:426-890`, especially `draft():720-846`, seeds one row per active sequence, then runs one autoregressive draft decode per depth. Each active sequence contributes one row at that depth. A D-token chain needs approximately D sequential draft decoder calls including its seed, not one D-row call. The predicted hidden state from one call feeds the next. Independent slots can share a call; future positions of the same chain cannot simply be put into that call without changing the model/proposal method.
2. **Per-sequence caps currently truncate after computation.** The server computes remaining-context/output limits in `tools/server/server-context.cpp:483` and passes `dp.n_max` at roughly line 3028. EAGLE's inner loop stops at global `params.n_max` (line 814), not `dp.n_max`. `common_speculative_draft():2845+` resizes the finished result afterward. A policy implemented only through `dp.n_max` reduces verification rows but leaves extra draft steps, sampler calls, and cache work. Genuine early caps must enter the EAGLE loop before the next decode. Retain wrapper truncation as a defensive limit.
3. **Confidence is not target acceptance probability.** EAGLE constructs a top-10 draft sampler (`speculative.cpp:491+`), samples, sorts, and uses candidate zero. The normal CPU chain appends `dist` (`common/sampling.cpp:399+`), which softmax-normalizes the surviving candidates. Therefore the top probability is conditional on top-10 retention. Mathematically it is at least 0.1 when at most ten valid candidates remain, so `p_min=0.1` with the strict `<` check normally duplicates zero on that path. Backend sampling is enabled by default; audit actual candidate size/normalization and CPU/backend parity before amending the frozen grid. Do not silently substitute thresholds after observing development outcomes. Calibration must be specific to precision, depth, context, and sampler path; a damaged quantizer may be confidently wrong.
4. **The confidence check has already paid for the current row.** `speculative.cpp:799` runs after draft decode and sampling. It can avoid future calls and target verification rows, but cannot refund that row's compute. If the first proposal fails confidence, the seed and feature maintenance still cost time. `n_min` can discard a short proposal after its work is done (line 839); it is not an early compute limiter.
5. **Draft `process()` is substantial unmeasured work.** `speculative.cpp:571-716` copies three target feature layers to host buffers, fuses every row with `llama_encode`, constructs shifted token/feature pairs, decodes draft context rows, and snapshots fused rows. The server invokes it after target decode and before acceptance (`server-context.cpp:3739-3755`). It processes the entire verification batch, including rejected suffix rows. Its source comment explicitly identifies the waste and proposes deferral (lines 421-425). `common_speculative_process()` has no current `t_draft_us` scope; the old `draft_ms` omits it. Another analysis owns head/KV-only graph pruning; that is complementary to skipping rejected rows, not evidence that all `process()` cost can disappear.
6. **Acceptance rebases a deferred boundary, not just a count.** `accept():848+` selects fused feature row `min(n_accepted,n_rows-1)` and updates pending position. The next seed pairs the fresh target token with this feature. The draft's position-P input is `(token[P+1], g[P])`. Any deferral must preserve that shift, accepted-prefix KV, the correction/bonus-token boundary, and cross-ubatch bridges. Simply keeping autoregressively drafted KV is invalid: verified target features replace predicted features.
7. **Server overhead includes provisional cache work and sampling.** `server-context.cpp:3050+` trims draft cache and optionally checkpoints; `3910+` clones the target sampler, verifies, handles rollback/checkpoint replay, updates metrics, trims target memory, then emits tokens until stopping. Qwen3 is not automatically paying the expensive recurrent-model replay branch: record actual `seq_rm` capability rather than attributing all generic code paths to this target. `common_sampler_sample():593` synchronizes the context before sampling. Draft backend sampling already exists (`--[no-]spec-draft-backend-sampling`); verify its benefit and semantics before building another sampler path.
8. **Stop accounting is subtle.** The server increments accepted and round counters before its output loop can stop on EOS/stop-string/output cap (`server-context.cpp:3971-4020`). Initial target tokens, final capped rounds, empty proposals, and replays can make emitted tokens differ from `rounds + accepted_drafts`. Collect actual emitted counts, verified-but-unemitted tokens, draft steps computed, proposals returned, and proposals verified separately.

## A cost and acceptance model suitable for decisions

For round r, record:

- L_r: proposals handed to verifier; H_r: draft positions actually computed; A_r: accepted draft tokens; E_r: actually emitted output tokens including target tokens. Usually H_r >= L_r, sometimes strictly because of confidence, caps, and `n_min`.
- C_r: complete round wall time, with nonoverlapping attribution to target verification V, draft generation D, feature/cache reconciliation F, sampler/rollback/host overhead O. Add queue/prefill terms separately for request latency and serving capacity. GPU spans may overlap and cannot simply be summed.
- State x: context length, remaining output budget, candidate confidence/margin, precision, active-sequence count, current batch occupancy, and cache mode.

For a long enough matched decode, throughput is `sum(E_r)/sum(C_r)` including non-speculative rounds. It is not `mean(A_r)/mean(D_r)`, `mean(E_r/C_r)`, or arithmetic mean of prompt speedups. Boundary costs need explicit inclusion when outputs are short.

For an uncensored chain at fixed policy/state, define `S_j = P(A >= j)` and conditional prefix survival `a_j = P(A >= j | A >= j-1)`. Then `S_j = product(a_k, k=1..j)` and `E[A] = sum(S_j, j=1..D)`. Only in a nonterminal ordinary round with exactly one emitted target token is `E[E] = 1 + sum(S_j)`. The survival curve is empirical; aggregate acceptance 23.72% does not mean every position independently succeeds with probability 0.2372. For confidence-adaptive lengths, also record at-risk/proposed counts by depth and avoid treating unproposed suffixes as observed model mistakes. Policy selection makes these samples censored and correlated.

At a candidate decision, extending a policy from `(E,C)` to `(E+delta_E,C+delta_C)` improves its ratio iff `delta_E/delta_C > E/C` for positive delta_C. To beat an incumbent measured rate G*, require `E_new - G* C_new > 0`. For a one-position chain extension with unchanged earlier proposal/verifier behavior, delta_E is S_(D+1). Its delta_C includes the next draft call, extra target rows, process/cache work, and changed launch/batch behavior, not just a matrix multiply. At Q4_0's historical 91.508 token/s, each extra millisecond must buy more than 0.0915 expected emitted tokens. This is a planning threshold, not a measured policy gain; rerun the anchor on a new build.

For a tree, replace S_j with probability the exact target-selected path is present through depth j. Distinct nodes, not sums of root-to-leaf lengths, determine row work. Sibling probabilities at a prefix must use target path mass (or measured greedy alternative coverage), not the sum of uncalibrated draft softmax scores. A branch that is never on the selected path has zero reward but still consumes decode, verification, and cache resources. Apply the same marginal reward/cost rule.

The evaluation's zero-draft-cost screen should be computed with actual E and full round spans. If all removable drafter work is Z, the optimistic unchanged-trajectory rate is `sum(E)/(sum(C)-sum(Z))`. If it cannot beat both FP16 and Q4_0, reject kernel-only investment at that quality/policy. Removing just the historical `draft()` timer is a narrower counterfactual; `process()` and feature extraction remain. No isolated verifier or emitted/round totals exist in the local historical reports, so a numerical verifier floor cannot be honestly reconstructed here. Quality or depth changes alter verification shapes, correction frequency, F and O; do not freeze all these costs to claim a universal required acceptance.

One simple measured scale: at unchanged emissions, all-nine W1A1 must reduce decode time per emitted token by about 49.4% to match the historical Q4_0 rate; head-only needs about 18.2%. These follow directly from rate ratios. They are not predictions that removing a particular timer achieves those reductions.

## Ranked actionable policies and bounded experiments

### 1. Fixed short chains and a real per-sequence cap

**Why first:** Existing D=5 spends almost five proposals/round even for all-nine W1A1 with near-zero useful prefixes. This is the least invasive policy screen and already belongs to the active protocol.

**Experiment:** Keep the mandated common D=5/p_min=0 primary precision matrix. On the frozen development set run the declared D={1,2,3,5}, p_min={0,0.1,0.3} diagnostics, with real computed-depth/returned-length traces. Audit the possible 0.1 redundancy first; any amendment must be predeclared. Set/report `n_min` explicitly. Include ordinary FP16 and Q4_0 at each policy, and separate common-policy comparisons from per-format tuned optima. Do not spend the reserved QAT-final set.

**Next small change if warranted:** Honor `min(global n_max, positive dp.n_max)` inside the EAGLE loop, including before queueing the next decode. Use remaining output/context budgets immediately. A separately frozen adaptive policy can choose among D={1,2,3,5} from development survival/cost estimates, updated only from past rounds, with conservative fallback and hysteresis. Avoid a high-capacity predictor on 24 development prompts. Use one simple precision-specific threshold table first.

**Go/no-go:** Require actual fewer draft decodes, not just shorter returned proposals; no boundary/cache/sampling failures; paired complete-decode improvement with request/TTFT regressions disclosed. For a W1Ax success claim require improvement over both FP16 and Q4_0, each with fair policy controls. Depth-1 still slower than a true no-speculation run and low first-position survival is a strong reason to stop scheduling optimization of that untrained format and return to quality work.

**Code:** `common/speculative.cpp:720-846`, `common_speculative_draft():2845+`, `common/speculative.h:common_speculative_draft_params`, `server-context.cpp:get_n_draft_max` and generating-slot setup; `scripts/benchmark_native_eagle.py` for new event/count capture.

### 2. Defer reconciliation until acceptance; combine with graph pruning only after separate attribution

**Why:** Current process eagerly does draft work for rows later discarded. At a five-token proposal, low A makes the wasted suffix especially large. This addresses work missed by historical `draft_ms`.

**Experiment sequence:** First instrument target verification -> process -> accept -> next seed, with processed row counts. Then a prototype stashes target features at verification time and performs fusion/cache rebuild only for committed prefix rows plus the needed boundary; keep prefill and cross-ubatch behavior unchanged initially. Compare deferred processing alone, graph-pruning alone (other owner), and combined only after each passes. At acceptance A, required fused data includes rows 0..A and required token/feature pairs depend on the shift; validate exact positions rather than blindly using A or A+1 as a universal decoder row count.

**Costs/risks:** Stashing unfused three-layer features can be larger than current fused snapshots, and delayed copies may change synchronization. Hold source buffers safely before target context reuse; preserve per-sequence contiguous grouping and microbatch order. Deferral must also service rounds with no usable draft and retain state for later drafting. Reusing predicted draft KV instead of recomputing target-feature-conditioned KV is a semantic change. Test all-rejected, all-accepted, partial-prefix, EOS, output cap, multi-ubatch prompt, and two-sequence interleaving cases using existing harnesses. This changes draft batch shapes and may change subsequent proposals through floating rounding; target weights remaining fixed is not a parity proof.

**Go/no-go:** Measured skipped row/graph work must exceed added storage/launch/copy cost in complete round time. Reject if the full decoder is slower despite a smaller isolated fusion timer. Verify outputs/state against current behavior, and inspect first divergences rather than silently broadening tolerance.

### 3. Load-aware independent-request batching, a separate serving objective

**Why:** Native EAGLE already collects one row per active sequence per depth; this is the least invasive source of useful larger N. No discarded branch is needed merely to fill a tensor tile.

**Bounded experiment:** After single-request results are frozen, evaluate concurrency C={1,2,4}, and C=8 only if target+draft KV/scratch fits with safety margin. Same request distribution, per-request context/output budgets, sampling, target precision, and model residency; compare target-only, FP16, Q4_0, and one selected W1Ax. Run a saturated fixed-backlog test and a small fixed-arrival test. Measure aggregate emitted tokens/wall second, per-request TTFT/inter-token/request p50/p95, queue time, completion rate, peak memory, active-row count per draft depth, and target verification rows. C target requests each with L proposals require approximately C*(L+1) verifier rows, while each draft step has at most C live rows, declining after early stops. Context length varies and remains a separate shape dimension.

**Scheduler choices:** Initially use existing continuous batching and no artificial wait. If tails suffer, shorten draft depth as verified batch occupancy/backlog rises. Only later test bounded batching delay with a specified latency budget; waiting for more requests improves utilization at the cost of TTFT. Long low-quality draft chains delay target verification for every slot in the common loop. Ragged depths should stop individual sequences while allowing others to continue; choose depth based on marginal full-batch cost, since removing one row may not remove a GPU launch. Test long-prompt admission/prefill separately to expose decode starvation.

**Go/no-go:** Gains must beat the same-concurrency Q4_0 and FP16 anchors within a predeclared latency budget. Never compare batched W1Ax aggregate throughput against batch-1 EAGLE. Target-only batching also amortizes weights and may reduce speculative advantage. Do not reduce target precision or per-request context just to fit concurrency and present it as a matched gain.

**Limits:** The historical matrix peaked at 10,160 MiB used and only 868 MiB free on an 11,264 MiB GPU. That is limited headroom, not evidence that eight or 37 independent requests fit. Shared model weights do not remove per-request KV and output-logit/feature scratch. Output and ubatch constraints must be inspected: `common_speculative_get_output_limits` at `speculative.cpp:2607`, plus `server-context.cpp:3790` rejects speculative row groups split across unsupported target sub-batches. One 37-row prefill/process observation cannot establish a feasible steady-state 37-request workload.

### 4. Shallow width expansion only if alternative coverage supports it

**Why conditional:** The native EAGLE implementation has no branch-width parameter in its chain loop. A separate `examples/speculative/speculative.cpp` implements tree-style branching, sequence KV copying, and branch acceptance, but is not the server EAGLE implementation. Native EAGLE `process()` asserts one sequence ID per token, and assumes each sequence's rows are contiguous. Shared ancestor rows/tree sequence memberships therefore require real feature/state/mask integration.

**Screen before implementation:** On development captures, measure first-rejection target-token rank among draft top-2/top-4 candidates and vocabulary coverage. Low top-1 acceptance with high top-2 coverage could justify a small root fork; diffuse errors or target tokens outside the 32k draft vocabulary cannot be repaired cheaply by width. Record target logits at relevant prefix, not hidden-state guesses on a wrong continuation.

**Bounded candidate:** One extra branch at an early uncertain node, width <=2, depth <=3, fixed total unique-node budget, compared to a chain at equal target-row budget and to tuned Q4_0. Measure probability of reaching each retained node, accepted-path length, wasted verified nodes, KV overhead, and complete wall time. Do not expand a full b^D tree. Branching may increase draft N but target verification work and masks grow, too.

**Gate:** Require predicted additional correct-path reward to pass the marginal-cost test on measured target-row and draft-row timings, then prove cache/mask/sampling correctness before performance. This is a later experiment, not a recommendation to alter the current W1Ax matrix.

### 5. Block proposal as a separate architecture/policy track

The pinned runtime already includes DFlash/DSpark-style block builders (`common/speculative.cpp:1197-1323`): noise blocks for all active sequences go through one `llama_decode`, then proposals are read/truncated. This removes repeated host-level model calls compared with EAGLE chains; it does not prove removal of all sequential computation. The architecture analysis reports that DSpark's Markov head retains an in-graph per-position argmax chain and N equals number of blocks there (N=1 for a single request). Respect that distinction in shape and speed claims.

Confidence truncation after a block is computed mainly saves verifier rows; changing actual block size is needed to save most block-generation work and may not be supported equally by a trained model. A block drafter needs compatible trained weights/features and a separate quality audit; EAGLE cannot be made block-parallel by batching its unknown future tokens. Use architecture-owner screening, then match target/verifier/sampling and compare full round costs against tuned FP16/Q4_0 EAGLE. Do not infer speed from model-call count or N alone.

## Sampling and numerical invariants

The server's `common_sampler_sample_and_accept_n` (`common/sampling.cpp:678-706`) samples from the target at each valid prefix, emits that token, and continues only when it equals the draft token. It is target-sample-and-match, not the usual draft-proposal `min(1,p/q)` acceptance plus residual correction. Arbitrary deterministic drafter proposals and history-only stop policies can preserve the target distribution under this algorithm, provided target conditional logits and sampler state are correct; quality affects match rate. The draft's 32k vocabulary limits acceptance but does not justify truncating the target distribution.

The separate tree example contains p/q and residual-distribution code (`examples/speculative/speculative.cpp:260-380`); do not transplant its acceptance logic without validating its actual proposal law, support mapping, and branch selection. A simpler exact conceptual tree verifier samples one target token at each selected prefix, follows the matching child if present, otherwise ends the round with that sampled token. It does not select the most favorable verified branch after seeing multiple future outcomes, or use draft confidence as a target acceptance probability. Finite-state grammar, penalties, reasoning budgets, and RNG state must advance once per emitted token along the chosen path. Rejected/unused paths must not mutate those states.

Changed D, width, concurrency, prefill coexistence, and microbatching change the target's numerical execution shape. Existing greedy target-only mismatches demonstrate that unchanged weights/FP16 precision are insufficient to assert token identity. Check raw IDs and first-divergence verifier logits against matched anchors for every policy; distinguish a wrong cache/position/mask from numerical argmax sensitivity. For stochastic decoding, validate the distribution/proposal semantics and state transitions rather than demanding identical seeded strings after scheduling changes. Synthetic-acceptance flags explicitly generate invalid output and may isolate a cost surface, never validate quality or count as a production speed result.

## Recommended order and stopping rule

Keep the active W1Ax fixed-policy matrix intact. Add the already-planned complete-round/count instrumentation, execute the declared development D/p_min diagnostic after confidence audit, and use its survival curves to decide if a true early-cap change or accepted-prefix reconciliation is worth a bounded implementation. Benchmark independent-request batching as a new serving track only after its latency objective and memory budget are defined. Defer trees and block drafters until their coverage/quality evidence passes a screening gate.

Stop performance work on an untrained precision/policy when the measured optimistic removable-drafter-cost bound fails against either mandatory anchor, or when additional depth/width has lower marginal emitted-token yield than the incumbent throughput. A policy that merely avoids wasted speculation can be useful operationally, but a W1Ax research win still requires repeated native end-to-end gains over both FP16 and Q4_0 under matched conditions.
