# Non-EAGLE architectures for genuine W1A1 drafting

> **Primary-source revision, 2026-09-25:** The external check changes the lead normal-precision quality candidate to **DSpark with matched DFlash as control**. It does not establish a W1A1 ranking. Released paired checkpoints improve feasibility, while default training remains outside this bounded project. See [primary evidence and admission gates](../research-cross-reference-2026-09-25.md#2-architecture-dspark-leads-a-paired-screen). The original audit below was local-only; this update incorporates web research.

Initial advisory analysis, 2026-09-25, used no web search, GPU work, implementation, or repository changes; the later web cross-reference is identified above. The active goal remains the all-layer W1Ax activation-precision suite; `docs/STATUS.md` puts acceptance-focused EAGLE QAT next and architecture screening later. An architecture change requires the user's decision.

## Recommendation

The most defensible next non-EAGLE experiment is a **small paired screen of a target-conditioned, one-pass block drafter and its semi-autoregressive-head variant**, using the locally documented Qwen3-4B DFlash/DSpark paths if their checkpoints and reference implementations can be acquired and audited in a later authorized experiment. These change a demonstrated limitation—repeated tiny token batches—without requiring a new serving engine. They do **not** have demonstrated W1A1 robustness. Quality recovery, sufficient binary coverage, and whole-round cost must all pass before kernel investment.

My practical ordering is:

1. **DSpark-style block transformer plus a small normal-precision Markov head**, as the lead reference-quality candidate after primary-source cross-checking; its N=1 and W1A1 costs remain open.
2. **Matched DFlash-style block-parallel transformer**, in the same screen as the required control for the value and cost of added token conditioning. Prefer paired releases over independently trained checkpoints when attributing an architecture effect.
3. **Target-conditioned lightweight multi-token heads**, including a Hydra-style conditioned variant rather than assuming independent Medusa-style heads are best. Admit this family only if block checkpoints fail or a compatible artifact makes the test bounded.
4. **A small autoregressive transformer**, useful as a control for weight versus activation fragility, but a weaker binary acceleration bet at one request because it retains sequential N=1 drafting and often more depth than EAGLE.
5. **Recurrent/state-space drafter**, deferred. Low state cost is not evidence of binary-friendly recurrence; it adds training, rollback, and precision questions without resolving the demonstrated first bottleneck.

This ranks the cost and information value of the next experiments, not measured throughput or established one-bit quality. No architecture in this list currently has a local W1A1 acceptance or speed result.

## Evidence boundaries

All measured claims below come from repository reports; architectural implementation claims come from local source at inspected llama.cpp HEAD `34e21b7d85c17e25d5a91ce2ab1074d4c18bfe39`. The current checkout could receive concurrent changes, so a future run must pin its own commit and dirty diff. No linked external paper, checkpoint, model card, or benchmark was opened in the initial local audit; the subsequent primary-source review linked above supersedes that evidence boundary for its cited claims. The local related-work note is prior project evidence, not a fresh independent literature verification. Descriptions of generic parallel-head, small-AR, and state-space design tradeoffs are architectural reasoning from model memory, **unverified against external current implementations**. Their quality and training-cost assessments are hypotheses.

The decision-relevant local results are unusually clear:

- On RTX 2080 Ti/SM75 with the fixed FP16 Qwen3 target, native all-nine W1A1 EAGLE fell to **0.055 accepted drafts/round versus 1.168** for ordinary EAGLE, and **0.561× decode throughput**. Its measured host draft-call cost fell from **6.471 to 3.558 ms/round**, but verification rounds rose from 3,400 to 6,940. The problem is not a missing binary instruction alone.
- Head-only W1A1 retained more quality, **0.860 accepted drafts/round**, but reached **0.907× ordinary decode throughput**. Actual SM75 binary-MMA versus portable binary head execution was **1.002×**, paired interval **0.997–1.006**. These are native packed W1A1 results, not fake-quant timing.
- The native Q4_0 EAGLE anchor reached **1.109× ordinary decode throughput**, with **1.182 accepted drafts/round**. A future candidate has a better alternative to beat than FP16 alone.
- The isolated real-shape trace found W8A8/W4A4 matrix instructions slower at **N=1**, faster at **N=37**. This is evidence that token batch shape matters in the implemented kernels. It is **not** a binary-MMA crossover measurement, nor evidence that N=7/8/15/16 would already win.
- The first head QAT pilot improved cached validation KL while worsening live acceptance. It warns against choosing an architecture or checkpoint by isolated logits or teacher-forced error alone.

Sources: `experiments/rtx2080ti-synthesis.md`, `experiments/rtx2080ti-quantization-suite.md`, `experiments/qat-revisit-plan.md`, `docs/PROJECT_OVERVIEW.md`, `docs/EVALUATION.md`.

The existing target-only versus speculative output mismatch remains unresolved at the strict-equivalence level. Candidate-to-anchor timing can be measured, but no new architecture inherits a lossless-decoding claim from the existing EAGLE run.

## What would make an architecture genuinely binary-friendly?

Use `Y[M,N] = W[M,K] X[K,N]`: **N is simultaneous token/position columns**, not vocabulary rows, width, number of learned heads, or tree nodes counted across different calls.

A useful candidate needs four properties together:

1. Enough conditional predictive information survives sign(W) and sign(X). Removing activation magnitudes is a different problem from compressing weights. Attention projections, token-conditioned fusion, and the vocabulary head can remain fragile even in a parallel graph.
2. A substantial fraction of measured cost sits in sufficiently wide, repeated matrix operations that share weights across multiple active N columns. Bigger blocks may amortize weights and launches; they also spend compute on suffixes discarded after an early rejection.
3. Short critical path after including feature extraction/injection, attention, normalization, output scoring, sampling, and state management. One `llama_decode` invocation is not proof of parallel dependencies inside its graph.
4. Training starts from useful conditional weights and can recover live accepted-prefix length within a bounded small-drafter budget. Training a new foundational binary language model would leave this project's scope.

Keep ordinary-precision residual paths, norms, softmax, scales, and state where needed and report them. That is consistent with the project's selected-linear W1A1 definition. Conversely, if the entire expensive output projection remains FP16, call the result a **W1A1 backbone with FP16 head**, and show its coverage/cost rather than calling it a fully binary drafter.

**W1A16 is diagnostic, not the endpoint:** ±1 weights with FP16 activations preserve much more activation information and do not use the same single XOR/POPCOUNT dot contract. W1A16 success with W1A1 failure is evidence to work on activation representation or quantization-aware training, not evidence that one-bit operands work. Ternary {-1,0,+1} weights are not one-bit weights; a ternary or commonly named “1.58-bit” model with higher-precision activations is not W1A1. Multiple residual bit planes, multi-branch binary sums, or widened replicas may help accuracy, but count every packed pass, scale, residual and extra parameter: their cost is not one W1A1 dot. Names or compressed checkpoint sizes do not establish executed precision.

## What the local DFlash/DSpark code actually establishes

`third_party/llama.cpp/docs/speculative.md` contains Qwen3-4B DFlash and DSpark conversion/server examples. This is stronger than an architecture mentioned in a paper, but weaker than a successful project model run. Do not claim the named remote artifacts have been acquired, audited, trained, or benchmarked locally.

In `common/speculative.cpp:999–1001`, DFlash's anchor plus mask block yields at most block_size−1 draft tokens; anchor-first DSpark can yield block_size. `:1190–1328` forms the block batch, calls one draft decode, and reads proposals. This means equal advertised block sizes need not mean equal proposed counts or equal matrices. A future comparison should record actual N and emitted/proposed positions.

In `src/models/dflash.cpp:569–810`, the decoder has separate feature-injection and noise-block modes, loops through layers, uses normal attention/FFN paths, and takes its output projection from the target when it has no private one. That shared head is a major coverage question: **never alter the target head in place to make the draft binary**. A separate packed draft copy would need new loader/export/graph plumbing and would trade extra memory for separate precision; retaining the shared FP16 head may cap speedup. Check checkpoint metadata before assuming either case or inventing its parameter count.

In `src/models/dflash.cpp:294–385`, DSpark looks up a low-rank row by previous token, computes a vocabulary bias for each position, adds it to base logits, and chooses argmax for the next position's conditioning. The source explicitly warns that this conditioning chain is greedy even when final picks use sampling parameters. This does not by itself prove incorrect target sampling: a verifier can remain correct with deterministic candidate construction. It **does** forbid assuming that the final sampled tokens follow the autoregressive q distribution one might infer from those logits.

The implementation also contains newer DFlash selector/convolution branches and additional backbones; they were not assessed as candidates. Documentation and source breadth are not reasons to expand the screen. Pick one exact checkpoint and identify its path before reasoning about cost.

The existing packed W1A1 metadata and dispatch in `src/models/eagle3.cpp` are architecture-specific. Reusing GGML binary math is plausible; non-EAGLE export, tensors, selective graph replacement, reference parity, and checkpoint audit are still work. Do not describe this as zero-effort native binary support.

## Verification semantics to preserve

For the first screen use greedy target verification. A drafter can propose any token block, including a deterministic block with non-causal internal attention, provided target scoring evaluates each candidate prefix causally, accepts only the matching prefix, emits the target correction/bonus token correctly, and restores state correctly. Internal bidirectional draft attention is not permission for target attention to see future draft tokens.

Per-position agreement is insufficient. Let S_i=P(first i drafted tokens all accepted). Then expected accepted draft tokens is sum_i S_i for a fixed maximum block length. A block with good isolated late-position accuracy but a weak first token contributes little. Measure the accepted-prefix survival curve, emitted tokens/round, first-rejection position, EOS and special-token behavior, and the live round trajectory. Evaluate each model's naturally valid conditional graph; do not force its independent marginals into an autoregressive likelihood interpretation.

For later stochastic evaluation, identify the actual verifier algorithm. A ratio/residual speculative sampler needs the correct proposal probabilities on the realized prefix; a block or Markov procedure's per-position scores are not automatically those probabilities. A target-sampled matching scheme has different requirements and acceptance properties. The audit must include the actual sampling path, target causal mask and caches; seeded token identity is not the distributional criterion. Do not make a lossless stochastic claim until this is settled.

## A small quality-first screen before kernels

This is a proposed later experiment, not an instruction to start another goal now.

1. **Admission and baseline gate.** Select paired released DSpark and DFlash checkpoints for the unchanged Qwen3-4B target, if their conversion and reference checks pass. Start with scheduling disabled; record target thinking mode and actual proposed-token counts. Do not reproduce the authors' default large-scale training pipeline or infer that a reported smaller-layer ablation is a released checkpoint. Pin local files/config/hash, trained block limits, tokenizer, vocabulary mapping, shared/private head, target taps, actual layers/widths, and needed memory. Produce a normal-precision forward/reference check and a greedy verifier parity diagnostic. If one model lacks a runnable trustworthy reference or cannot fit with the fixed target, drop it from this bounded screen rather than change targets or build broad support.
2. **Freeze a small comparison.** Let the data/evaluation owners allocate independent architecture-development and final prompts; do not reuse the sealed 12 historical prompts to select winners or silently repurpose the frozen EAGLE QAT final set. Start with a small development subset for rapid gates, balanced across code/prose/reasoning and more than one context length. Compare only a short block and the checkpoint's trained block limit, or a fixed valid intermediate length if memory requires it. Do not conduct a broad block-size sweep.
3. **Run a factorized fake-quant diagnostic, with timing clearly excluded.** For each admitted model compare its FP16/BF16 reference, W1A16 backbone, W1A1 backbone with original head, and selected W1A1 groups (FFN first, then attention/fusion as needed). Include the head separately after auditing whether it is shared. Record precision of every exception. W1A16 determines whether activation sign loss is the extra quality barrier; FFN/head ablations identify cost that could be made binary without losing the prefix. Stop poor groups instead of requiring all-layer binary purity.
4. **Evaluate live acceptance, not only teacher-forced agreement.** Capture per-position survival, accepted/proposed totals, emitted tokens/round, verifier work, and trajectories on candidate-generated states. Compare precision variants under the same architecture/verifier. Keep unquantized DFlash/DSpark as their own anchors and FP16/Q4_0 EAGLE as the practical alternatives. A non-EAGLE architecture win is not automatically a W1A1 win.
5. **At most one bounded recovery recipe per surviving family.** Have the QAT owner select the target-aligned objective and budget before training, using development live acceptance to select checkpoints and the held-out final set once. Train only drafter parameters; keep target fixed. Require the normal-precision trained-weight control to reveal whether training itself hurts quality, as happened in the first EAGLE head pilot. No foundation-model training or indefinite rescue sweeps.
6. **Compute a candidate-specific time budget before binary engineering.** Measure normal-precision draft decomposition, actual M/K/N histogram, feature injection, head, verification and other overhead on the intended hardware. Let E be emitted tokens/round and C_v+C_o be verification plus unavoidable other cost. The optimistic bound E/(C_v+C_o), setting draft time to zero, must beat both measured FP16 and Q4_0 EAGLE rates. More specifically, at required rate R*=max(R_FP16,R_Q4), allowed draft budget is E/R*−C_v−C_o. A nonpositive budget stops kernel work; a tiny budget compared with measured non-binary draft scaffolding stops it too. This is a measured-workload planning bound, not a speed result; target cost can change with block size, accepted prefix, and numerical path.
7. **Only one native candidate graduates.** Require a positive realistic budget after non-binary head/attention/packing costs and encouraging live quality. Then reuse the existing binary correctness machinery with the new real shapes and packing contract. Measure same-device RTX 2080 Ti packing-inclusive layers and full rounds against its unquantized/ordinary-low-bit architecture controls, FP16 EAGLE, and Q4_0 EAGLE. A faster block FP16 implementation can otherwise masquerade as a binary benefit. Final selection follows repeated end-to-end timing, not matrix peak throughput.

Do not impose an arbitrary universal acceptance threshold such as “at least two tokens.” The sufficient threshold depends on target verification cost, block size, draft cost and the Q4_0 anchor. Prefix survival plus this budget is the decision rule.

## Failure and stop gates

- **First-token or early-prefix failure:** If W1A1 loses the early prefix badly and one bounded target-aligned recovery recipe does not restore a feasible time budget, stop that family/coverage. High late-position token accuracy does not rescue it.
- **Only W1A16 survives:** Report the architecture as activation-sensitive. It may be useful for the current precision study, but do not promote it as evidence for the W1A1 endpoint.
- **Mask-position collapse:** Inspect whether equal sign patterns erase positional/context information across masked states. If the block is near-repetitive after quantization, precision exceptions or an explicitly changed representation require new accounting; do not infer parallel tokens equal useful diversity.
- **Low coverage:** If required FP16 vocabulary scoring, attention, KV injection, Markov work and scheduling consume almost all draft time, the theoretical binary saving is too small. Stop unless the measured bound remains worthwhile.
- **Hardware-shape failure:** If actual N is too small to help after padding, packing and launch costs, stop native optimization. The N=37 INT result cannot justify larger-block binary execution without measurements.
- **Validation/semantics failure:** Unresolved mapping, label alignment, mask, cache rollback, or proposal-distribution errors block quality or speed claims. Do not “fix” quality by changing the target or accepting approximate tokens.
- **Scope failure:** No compatible checkpoint, larger-than-budget training, new runtime requirements, or repeated architectural redesign should produce a short negative feasibility report and a user decision, not silent goal expansion.

## Strongest counterarguments

**“A parallel block drafter could be less binary-robust than EAGLE.”** Correct. It has multiple transformer layers and many mask tokens, and may need more expressive activation magnitudes to predict uncertain future positions. The recommendation is to test this cheaply, not assume it away. Mixed-precision group ablations and W1A16 controls are essential.

**“DSpark could have the best quality and should be first.”** The primary-source follow-up strengthens that quality prior and revises the ranking accordingly. The paired DFlash control remains necessary, and neither normal-precision result proves binary robustness. The Markov head's N=1 chain must still be timed and should initially retain its ordinary precision.

**“A small autoregressive model may be much easier to train.”** Also plausible when a strong compatible checkpoint exists. Its clean baseline makes it a good fallback. But training convenience does not remove sequential depth or the one-column workload which already limited specialized matrix instructions locally.

**“Parallel heads would be much cheaper than a several-layer block model.”** They may be, and they deserve a small test if an appropriate pretrained artifact is available. Unconditional future heads can lose accepted-prefix quality, separate heads do not create shared-weight token batches, and no compatible Qwen3-4B path was established. A new head training effort should not displace the two source-supported candidates without evidence.

**“Why try an architecture at all when Q4_0 EAGLE already wins?”** For deployed throughput on this workload, Q4_0 EAGLE is the current measured winner among these controls. Binary research is justified only if it tests a concrete mechanism—quality-preserving sign representations plus useful block work—and uses Q4_0 as its threshold. A negative quality-first screen is an acceptable stopping result.

**“Could a binary-pretrained or ternary model settle the question?”** Not without matching operands, target task and execution. Ternary weights or one-bit weights with wide activations cannot answer true W1A1; a separate large pretrained model may have wrong tokenizer/target conditioning, much greater training cost, and no relevant serving baseline. Such a pivot is a major user decision.
