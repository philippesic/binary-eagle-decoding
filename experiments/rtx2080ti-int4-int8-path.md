# RTX 2080 Ti INT8 and INT4 EAGLE path audit

**Status:** static audit only, 2026-09-24. No CUDA build, GPU execution, SASS capture, GGUF conversion, or timing was performed. Parent revision `af5f337`; pinned llama.cpp gitlink `8d2b18a9c9b3a42927404a91799a823c758c09b6`.

## Arithmetic contract and scope

The earlier [PyTorch acceptance sweep](pytorch-int4-int8-cuda-acceptance.md) covered all nine draft linears: fusion, Q/K/V/O, gate/up/down, and head. Its W8A8 and W4A4 simulations use signed codes `[-127,127]` and `[-7,7]`, respectively, with F32 absmax scales **once per output row and once per token input vector**. Both operands are rounded to nearest even. A zero-scale vector gives zero codes. The simulation uses FP32 `F.linear` on integer-valued floats, multiplies row and token scales, adds bias if present, and casts to the input dtype. It establishes acceptance behavior, not native integer instruction use. All nine reduction widths (2,560, 4,096, 5,120, 7,680, or 9,728) are divisible by 32 ([shape audit](eagle3-graph-audit.md)).

The native target should preserve that quantizer, one row scale and one token scale, signed integer accumulation, output conversion, and exact nine-linear coverage. A matched comparison also needs the same ordinary EAGLE and target anchors on the 2080 Ti. The simulation's W8A8 accepted 2.1816 draft tokens per round versus 2.3166 ordinary; W4A4 accepted 0.2882. The known verifier/target greedy mismatch limits quality interpretation.

## What pinned GGML CUDA already executes

| Candidate | Stored weight / live activation | Likely SM75 operator by batch | Matches prior WnAn contract? |
| --- | --- | --- | --- |
| Ordinary FP16 EAGLE | F16 weight / graph F32 or F16 activation, subject to CUDA graph casts | FP16 vector/cuBLAS/Tensor Core path selected by layout and batch | Anchor only |
| Q8_0 GGUF | Signed 8-bit weight in 32-element blocks with F16 block scale / activation quantized on device to Q8_1 signed bytes with 32-element F16 scale | At `ne11 <= 8`, MMVQ performs signed-byte `DP4A` dots; above that, MMQ can use Turing signed INT8 MMA on eligible layouts | **No:** scales are per 32, not per row/token; conversion and rounding differ |
| Q4_0 GGUF | Packed offset 4-bit weight in 32-element blocks with F16 block scale / activation quantized on device to Q8_1 signed bytes with 32-element F16 scale | At `ne11 <= 8`, MMVQ extracts nibbles and performs nonnegative-byte × signed-byte `DP4A` with an offset correction; above that, MMQ expands Q4_0 to signed bytes and can use Turing signed INT8 MMA | **No:** activation is 8-bit, and neither branch executes INT4 × INT4 |
| Native W8A8 of prior sweep | Signed INT8 weight and activation, F32 row/token scales | **Absent** as a selectable EAGLE path; possible dedicated `GGML_W8A8_MUL_MAT` or a precisely matching GGML quant type | Pending |
| Native W4A4 of prior sweep | Signed packed INT4 weight and activation, F32 row/token scales | **Absent**; requires a new packed INT4 operator and SM75 `s4 × s4` implementation | Pending |

The GGUF rows are valid weight-format controls. Their runtime activation conversion means some operations do perform two-operand integer arithmetic; calling the artifacts simply “weight only” describes the **stored GGUF**, not every executed dot. In particular, Q8_0 × Q8_1 MMVQ is a genuine two-operand signed INT8 **arithmetic path**, although it is `DP4A` rather than a Tensor Core instruction and does not match the prior W8A8 **quantization contract**. Q4_0 × Q8_1 MMVQ directly reads packed 4-bit weight codes but computes with byte `DP4A`; it is a W4A8-like path, not a native INT4 Tensor Core path. Neither row can inherit the PyTorch W8A8/W4A4 acceptance numbers. Actual dispatch still requires a run-time trace, because source type, activation/destination type, stride, and batch select different paths.

The benchmark config sets `--parallel 1` and `--spec-draft-n-max 5`. The EAGLE3 `draft()` loop in `common/speculative.cpp` adds one input pair per active sequence and calls `llama_decode` after each proposed token; with one sequence, its iterative draft linears therefore have **one token column (`ne11 = 1`)**. The prefill/feature encoder and the `process()` reconciliation call can have larger batches and need separate tracing, but the critical repeated decode projection uses MMVQ when its F32 source/output and layout gates pass. This is a source-level dispatch prediction, not an observed SM75 trace. It also means the existing MMQ Turing INT8 Tensor Core branch is unlikely to represent steady-state draft latency in the frozen single-sequence benchmark.

Source trace in the pinned checkout:

- `ggml/src/ggml-cuda/ggml-cuda.cu`, `ggml_cuda_mul_mat`: the fast quantized branches require F32 `src1` and F32 output, select MMVQ before MMQ, and fall back to cuBLAS under other conditions. This is an operator selection rule, not proof that a particular EAGLE request enters MMQ.
- `ggml/src/ggml-cuda/mmvq.cu`, `mmvq.cuh`, and `vecdotq.cuh`: `MMVQ_MAX_BATCH_SIZE` is 8; MMVQ calls `quantize_row_q8_1_cuda` before its quantized vector kernel. The Turing default threshold for Q4_0 and Q8_0 is `ne11 <= 8`. The Q8_0 dot invokes `ggml_cuda_dp4a` on byte-packed codes. The Q4_0 dot extracts each nibble, invokes `ggml_cuda_dp4a` on those nonnegative byte lanes and Q8_1 signed bytes, then subtracts the zero-point contribution using the activation partial sum.
- `ggml/src/ggml-cuda/mmq.cu`: MMQ accepts Q4_0 and Q8_0, quantizes F32 `src1` through `quantize_mmq_q8_1_cuda`, and `ggml_cuda_should_use_mmq` returns true when Turing MMA is available (subject to minimum shared memory and earlier dispatch gates).
- `ggml/src/ggml-cuda/mmq.cuh`, `mmq-load-tiles.cuh`, `mmq-vec-dot.cuh`, and `mma.cuh`: the Turing MMA layout maps Q8_0 to Q8_1 signed-byte MMA. Q4_0 nibbles are expanded with a subtract-8 operation to signed bytes, then use the same `q8_0_q8_1_mma` dot. For SM75, `mma.cuh` emits `mma.sync.aligned.m8n8k16.row.col.s32.s8.s8.s32`; no `s4.s4` call appears in this CUDA path.
- `ggml/src/ggml-quants.c`: Q4_0 uses a 32-value block scale chosen with its max-sign rule and offset nibble codes; Q8_0 uses 32-value F16 scales. `ggml/src/ggml-cuda/quantize.cu` quantizes each Q8_1 activation block from its own absmax and uses `roundf`. These are not the prior whole-vector F32 scales and nearest-even PyTorch contract.

NVIDIA documents signed INT4 Tensor Core support for Turing and the `wmma.mma.sync.aligned.m8n8k32.row.col.s32.s4.s4.s32` instruction in its [PTX 10.2 ISA](https://docs.nvidia.com/cuda/archive/10.2/parallel-thread-execution/index.html); hardware capability alone does not provide the missing GGML operator. Its [CUDA 10.0 release notes](https://docs.nvidia.com/cuda/archive/10.0/cuda-toolkit-release-notes/) describe SM75 sub-byte support as experimental at introduction. This audit has not compiled an INT4 kernel with the current remote toolkit.

## Minimum correct native route

1. Add an opt-in EAGLE format with versioned metadata and strict coverage checks for all nine linears, paralleling the existing W1A1 loader/graph bridge. Convert the original weights directly to signed INT8 or signed packed INT4 plus **F32 row scales**; preserve Q/K row permutations and the absence of dense shadow tensors. Retain ordinary embeddings, norms, attention softmax, residuals, and verifier.
2. Add one runtime activation pack per input token with a **F32 token scale**, explicit zero-vector behavior, nearest-even signed codes, and a finite-value policy. The operator computes an INT32 dot, multiplies row and token scales in the documented order, and returns the graph's required output type. Handle any optional bias outside or inside the operator identically to the prior simulation.
3. First prove an SM75 INT8 path with existing `mma.cuh` signed-byte primitives or a dedicated vector dot for small token batches. Dispatch must not silently fall back to F16/cuBLAS while being labeled W8A8. The existing MMQ machinery is a useful template, but changing its 32-value scale semantics globally would alter current GGUF behavior.
4. Build W4A4 separately with both inputs packed as signed nibbles and a verified SM75 `s4.s4` instruction. An INT8 MMA over unpacked Q4_0 weights and Q8_1 activations is a distinct precision track. A decode vector fallback may be useful for small batches but must still consume INT4 × INT4 codes and be labeled by its actual instruction class.

This is a runtime/format change spanning converter, loader, GGML graph op, CUDA packing, dispatch, and backend tests. It exceeds a bounded isolated kernel edit. No implementation was started without a reviewable arithmetic/format plan and remote correctness gate.

## Validation gate before timing

For each width, compare CPU integer codes and exact INT32 dots to CUDA on adversarial and real EAGLE shapes: zeros, half-way rounding, saturation, both signs, the full 9,728-wide reduction, multiple tokens, and every covered output group. Check scales and outputs against the F32 reference with declared tolerances; distinguish expected accumulation-order differences from format errors. Confirm the GGUF tensor inventory and versioned metadata, run a local/SM75 backend op check, then compare draft logits, accepted counts, and token text against ordinary and simulated EAGLE on paired prompts. Capture kernel names, chosen GGML branch, and `nvdisasm`/`cuobjdump` SASS for **executed** SM75 kernels. The W8A8 evidence should show signed INT8 operands and integer dot; W4A4 additionally needs packed signed INT4 operands and INT4 MMA or an explicitly labeled INT4 vector dot. Only then measure packing-inclusive component and end-to-end time with the goal protocol.

## Stopping boundary and recommendation

Use Q8_0 and Q4_0 as their already prepared controls, recording their actual branch and activation format on the 2080 Ti. Keep native W8A8/W4A4 rows unmeasured until the new format/operator gates pass. Prioritize W8A8 because its simulated acceptance is near ordinary EAGLE; W4A4 currently has a severe acceptance loss that even a fast kernel may not overcome. The orchestrator can choose whether a follow-on implementation is justified after the existing W1A1 and weight-format suite is measured. No GPU resource or shared goal file was touched in this audit.
